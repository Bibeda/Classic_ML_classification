# 1. Постановка задачи

Задача: Бинарная классификация. Цель — предсказать, превышает ли годовой доход человека 50 000 долларов, на основе его социально-демографических характеристик.

Данные: Датасет Adult Income Dataset, содержащий 48 842 записи и 15 признаков. Целевая переменная `income` имеет два класса: `<=50K` (0) и `>50K` (1). Класс `<=50K` является доминирующим (~76% данных), что делает задачу несбалансированной.

Признаки:
    age: возраст
    workclass: тип работодателя
    fnlwgt: кол-во человек такого же типа, чисто техническая инфа которая не несёт в себе смысла
    education: уровень образования
    education-num: число лет обучения
    marital-status: семейное положение
    occupation: род занятий
    relationship: семейная роль
    race: раса
    sex: пол
    capital-gain: прирост капитала
    capital-loss: потеря капитала
    hours-per-week: рабочих часов в неделю
    native-country: страна происхождения
    class: уровень дохода (>50K / <=50K) --- TARGET


# 2. Первичный анализ и предобработка данных (EDA)

**Обработка пропусков:** В колонках `workclass`, `occupation` и `native-country` были обнаружены пропуски. Было принято решение заменить их на наиболее часто встречающееся значение в соответствующей колонке.

**Основные наблюдения по данным:**
1. Значения capital-gain и capital-loss имеют сильно скошенные распределения: у подавляющего большинства наблюдений они равны нулю.
2. education и educational-num содержат практически одну и ту же информацию, поэтому один из признаков можно удалить.
3.  `fnlwgt` не несёт смысловой нагрузки для предсказания дохода конкретного человека
4. Доход заметно связан с уровнем образования: люди без высшего образования значительно чаще относятся к классу <=50K, в то время как среди людей с Bachelor's, Master's, Doctorate и Prof-school доля дохода >50K существенно выше.
5. Семейное положение также связано с доходом. Для состоящих в браке доля класса >50K заметно выше, чем среди никогда не состоявших в браке.


**Feature Engineering:**
1.  Удаление неинформативных признаков: Колонки `fnlwgt` и `educational-num` были удалены. 

2.  Уменьшение кардинальности категориальных признаков: 
    *   `education`: Уровни образования были сгруппированы в 6 осмысленных групп: `School`, `HS-grad`, `Some-college`, `Assoc`, `Bachelors`, `Post-grad`.
    *   `native-country`: Страны были объединены в регионы: `US`, `Anglo`, `LatAm`, `Europe`, `Asia`.
    *   `marital-status`: Статусы были сгруппированы в `Married`, `Never married`, `Was married`, `Married-absent`.
    *   `race`: Расы были сгруппированы в `White`, `Black`, `Asian`, `Other`.
    *   `workclass`: Типы работодателей были сгруппированы в `Private`, `Gov`, `Entrepreneur`, `Self-emp`, `No-income`.
    *   `occupation`: Род занятий был сгруппирован в `High white-collar`, `Low white-collar`, `Sales`, `Service`, `Blue-collar`, `Other`.
    Это было необходимо, чтобы избавится от "проклятия размерности"

3.  Создание нового признака: На основе колонки `relationship` был создан бинарный признак `Own-child`, указывающий, является ли человек ребенком в семье.

**Кодирование признаков:** Для подготовки данных к подаче в модели был создан пайплайн предобработки с использованием `ColumnTransformer`:
*   Порядковые признаки (`education_group`): Кодировались с помощью `OrdinalEncoder`, так как между группами существует естественный порядок.
*   Номинальные признаки (`gender`, `country_group` и др.): Кодировались с помощью `OneHotEncoder`.
*   Числовые признаки: Передавались без изменений.

# **3. Построение безлайнов и сравнение моделей**

Для выбора базовой модели было обучено и оценено четыре алгоритма с использованием 5-фолдовой кросс-валидации:
*   Логистическая регрессия
*   Решающее дерево
*   Случайный лес
*   LightGBM

**Результаты:**

| Модель | ROC AUC |
| :--- | :--- |
| LogisticRegression | ~0.90 |
| DecisionTreeClassifier | ~0.88 |
| RandomForestClassifier | ~0.92 |
| **LGBMClassifier** | **~0.93** |

LightGBM показала наилучшие результаты и была выбрана в качестве основной модели для дальнейшей оптимизации.


# 4. Improvements и Feature Engineering

После построения baseline были проверены дополнительные преобразования признаков. Каждый эксперимент оценивался отдельно, чтобы определить его влияние на качество моделей. Рассматривать улучшения будем на примере ROC AUC.

### Биннинг возраста

Возраст был разбит на интервалы:

`0–25`, `25–35`, `35–45`, `45–55`, `55–65`, `65–100`.

Были проверены два варианта:

1. добавить категориальный `age_bins`, сохранив исходный возраст;
2. полностью заменить возраст на интервалы.

Для LightGBM:

- добавление `age_bins`: **+0.00005 ROC AUC**;
- замена исходного возраста на bins: **−0.00087 ROC AUC**.

Существенного прироста не произошло. Вероятная причина состоит в том, что деревья LightGBM и без ручного биннинга хорошо находят оптимальные границы разбиения непрерывного признака. Замена возраста на интервалы дополнительно приводит к потере информации.

При этом для Random Forest замена возраста на интервалы дала прирост ROC AUC примерно **+0.0041**, что показывает различную реакцию моделей на такое преобразование.

### Биннинг `hours-per-week`

Количество рабочих часов было разбито на интервалы шириной 10 часов.

Для LightGBM:

- добавление дополнительного binned-признака: **+0.00001 ROC AUC**;
- замена исходного значения на bins: **+0.00018 ROC AUC**.

Изменение находится на уровне статистического шума и значимого улучшения модели не даёт.

Как и в случае возраста, LightGBM способен самостоятельно находить подходящие границы разделения числового признака.

### Масштабирование `capital-gain` и `capital-loss`

Из-за сильно скошенного распределения `capital-gain` и `capital-loss` была проверена стандартизация с помощью `StandardScaler`.

Для LightGBM изменение ROC AUC составило практически **0**.

Это ожидаемый результат: деревья решений и основанные на них boosting-модели практически не чувствительны к масштабу признаков.

Для Logistic Regression стандартизация дала небольшой положительный эффект, однако он также оказался очень мал.

### Бинарные признаки наличия капитальных операций

Дополнительно были созданы:

- `has_capital_gain = capital-gain > 0`;
- `has_capital_loss = capital-loss > 0`.

Для LightGBM изменение ROC AUC составило около **−0.00001**, то есть улучшения практически не произошло.

Вероятно, исходные признаки уже содержат всю необходимую информацию, а LightGBM самостоятельно способен выделить нулевые и ненулевые значения с помощью split-ов.

### Работа с дисбалансом классов

Были проверены два подхода.

#### `class_weight='balanced'`

Для LightGBM:

- ROC AUC: **+0.00026**;
- Recall: **+0.0506**;
- Precision: **−0.0615**;
- F1: **−0.0176**;
- Accuracy: **−0.0426**.

Балансировка позволила модели находить больше объектов положительного класса, поэтому Recall вырос. Однако одновременно увеличилось количество false positives, что привело к падению Precision, F1 и Accuracy.

Таким образом, применение `class_weight='balanced'` может быть полезно в задаче, где особенно важен Recall, но для текущей целевой метрики существенного выигрыша оно не даёт.

#### SMOTE

Для LightGBM относительно baseline:

- ROC AUC: **−0.00251**;
- Recall: **+0.0299**;
- Precision: **−0.0372**;
- F1: **−0.00154**;
- Accuracy: **−0.0153**.

SMOTE увеличил полноту положительного класса, но ухудшил ROC AUC и Precision.

Поэтому SMOTE не был включён в финальный pipeline.

### Вывод по улучшениям

Ни одно из дополнительных преобразований не обеспечило заметного прироста ROC AUC для LightGBM.

Это можно объяснить тем, что градиентный бустинг по деревьям уже способен:

- моделировать нелинейные зависимости;
- автоматически находить пороги для числовых признаков;
- учитывать взаимодействия признаков;
- работать с признаками разного масштаба.

Поэтому ручной биннинг и масштабирование дают значительно меньше пользы, чем могли бы дать для линейной модели.

Лучшим решением оказалось сохранить относительно простой набор признаков и сосредоточиться на настройке самой модели.


# 5. Подбор гиперпараметров

Подбор гиперпараметров выполнялся для `LGBMClassifier`.

Основная метрика оптимизации — **ROC AUC**, оценка кандидатов выполнялась с помощью **5-fold cross-validation**.

Были протестированы три стратегии:

1. Grid Search;
2. Randomized Search;
3. Bayesian Search.

Baseline LightGBM в данном эксперименте имел:

**ROC AUC = 0.928708**.

### Grid Search

Перебирались параметры:

| Параметр | Значения |
|---|---|
| `num_leaves` | 15, 31, 63 |
| `max_depth` | 8, 10, 15 |
| `n_estimators` | 100, 200, 500 |

Лучшие параметры:

```python
{
    "max_depth": 8,
    "n_estimators": 200,
    "num_leaves": 15
}
```

Результат:

**ROC AUC = 0.929078**

### Randomized Search

Для более широкого пространства параметров использовались следующие диапазоны:

| Параметр | Диапазон |
|---|---|
| `num_leaves` | целые числа `[15, 31]` |
| `max_depth` | `-1`, `8`, `12`, `16` |
| `reg_alpha` | `0.01`, `0.1`, `1.0` |
| `reg_lambda` | `0.01`, `0.1`, `1.0` |
| `learning_rate` | непрерывный диапазон `[0.01, 0.11)` |
| `n_estimators` | `100`, `200`, `500`, `1000` |

Лучшие параметры:

```python
{
    "learning_rate": 0.1054,
    "max_depth": -1,
    "n_estimators": 200,
    "num_leaves": 17,
    "reg_alpha": 0.01,
    "reg_lambda": 0.01
}
```

Результат:

**ROC AUC = 0.928617**

### Bayesian Search

Для Bayesian Optimization использовался `BayesSearchCV` с Gaussian Process в качестве surrogate model.

Пространство поиска:

| Параметр | Диапазон |
|---|---|
| `num_leaves` | `[10, 25]` |
| `learning_rate` | `[0.01, 0.1]`, log-uniform |
| `n_estimators` | `[100, 1000]` |

Лучшие параметры:

```python
{
    "learning_rate": 0.0830,
    "n_estimators": 480,
    "num_leaves": 10
}
```

Результат:

**ROC AUC = 0.928887**


### Сравнение методов тюнинга

| Метод | ROC AUC | Δ к baseline |
|---|---:|---:|
| Baseline | 0.928708 | — |
| **Grid Search** | **0.929078** | **+0.000371** |
| Random Search | 0.928617 | −0.000091 |
| Bayesian Search | 0.928887 | +0.000179 |

Наилучший результат показал **Grid Search**:

```python
LGBMClassifier(
    max_depth=8,
    n_estimators=200,
    num_leaves=15
)
```

При этом различия между всеми вариантами крайне малы. Это говорит о том, что baseline-настройки LightGBM уже достаточно хорошо подходят для данного датасета, а дальнейшее увеличение сложности процедуры тюнинга не приводит к существенному улучшению качества.
